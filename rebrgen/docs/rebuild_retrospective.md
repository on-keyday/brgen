# 「0 から作り直すとしたら」の棚卸し

## この文書の位置づけ

ADR ではない。ADR は「判断とその理由」を記録するものだが、この文書は**判断していない**。
現アーキテクチャを読んだ上での (a) 継承すべきと言える決定、(b) 再考の材料がある点、を
測定と実コードに紐づけて並べただけのものである。作り直しの提案でも、移行計画でもない。

- 作成: 2026-08-05
- 対象: `brgen` (src/core, src/tool) + `rebrgen` (src/ebm, ebmgen, ebmcodegen, ebmcg, ebmip)
- 測定基準時点: 現 HEAD (`gen/ebmgen-cyclic-callee-params`)

「継承すべき」側は既に ADR が存在するものが多い。ここでの追加価値は、ADR が主張している
効果が**現在のツリーの数字で裏付けられるか**を確認した点にある。

## 1. 継承すべきと言える決定

### 1-1. IR は「意味論を落とさない」トランスパイラ IR にする — ADR 0003

BM で論理レイアウトまでフラット化し、後から意味を復元できなくなったという**実測された失敗**が
根拠になっている。ADR 0003 の「コンパイラとトランスパイラでは IR の設計方針が根本的に異なる」は、
一般論としてではなく BM→EBM の移行コストという実費で裏が取れている判断である。

作り直しても、この結論は変わらないと考えてよい根拠がある: 現在 15 言語のバックエンドが平均
1,473 行で成立しているのは、EBM が構造 (union、bit field、encode/decode 対称性) を保ったまま
渡しているからで、意味論を落とした IR からこれを復元するコストは BM 時代に一度払っている。

**限界**: ADR 0003 自身が「ID 参照ベースなのは深い設計思想ではなく実際的な制約の積み重ね」と
書いている。「意味論を保つ」は継承すべきだが、「全ノードに ID を振ってグラフで表現する」は
別の判断であり、そのまま継承する理由は ADR 上にない。ID 参照の帰結として
`access_helper.hpp` 10,691 行の生成アクセサと `get_field<"path">` API (§2-5) が要求されている。

### 1-2. IR の定義を自分の DSL で書く — ADR 0004

1,241 行の `.bgn` から 31,890 行の C++ シリアライザが出て、構造変更は `update_ebm.py` 一発で回る。
dogfooding が同時に「brgen が実用に耐えるか」の常時回帰テストになっている点が効いている
(EBM が壊れれば src2json/json2cpp2 の欠陥として即座に露見する)。

**限界**: 生成物のサイズがビルド時間を支配する側に回っている。CI が ccache 前提で組まれている
のはこの構造の帰結でもある。0 から作るなら「IR 定義を DSL で書く」は継承しつつ、生成される
シリアライザの粒度 (全フィールド分の encode/decode を展開するか) は別に測る価値がある。

### 1-3. メタジェネレーター + フック優先順位 — ADR 0009 / 0016 / 0047

15 言語が平均 1,473 行で立ち上がっているという数字が、この機構の効果そのものである。
共通展開 103 フック 4,033 行が言語非依存部分を吸収し、バックエンドは差分だけを書く。
ADR 0047 で per-lang 生成物 150 万行 → 共有 body + 7 行 wrapper に圧縮済み。

**限界**: フック発見が `__has_include` ベースであるため、手書きでフックを追加すると CMake が
依存を追跡できず silently 反映されない。`ebmtemplate.py` を必須にする運用でカバーしているが、
これは機構ではなく規律で塞いでいる穴である。ADR 0047 が記録している quote-include の探索順序制約
(共有 body の置き場所に `visitor/` を置いてはならない) も同じ機構の副作用。
0 から作るなら、フック集合をビルド時に glob して明示的なリストを生成する方式と比較する余地がある。

### 1-4. 生成器の実装言語を C++ に統一 — ADR 0019

brgen 側で json2go を Go、json2rust を Rust で実際に書いた上で「大した旨味がなかった」という
経験が根拠。実装言語が分散すると、ツールチェーン・メタ生成・共通フック層のいずれも共有できなくなる。
1 人 + AI 体制ではこれは純コストになる。**実験済みの判断**なので継承してよい。

### 1-5. 「何を切るか」を明文化する — ADR 0026

他のどの項目よりも上位に置くべき決定。writer 側の整合性自動修復と declarative 単一モデルを切り、
encode/decode 両対応を守る、という線引きが明文化されている。0 から作り直す場合に最初に読むべきは
このドキュメントであり、実装ではない。

### 1-6. e2e 優先 (ADR 0007) と測定駆動の方向決定 (ADR 0048)

ADR 0048 は「実在フォーマットをコーパスに追加する」という方針を**測定が否定した**実例として
残っている (245 個追加しても新構造は 3 種のみ)。設計方向を見立てではなく数字で決めた記録が
ツリーに残っていること自体が、作り直し時に継承すべき運用。

### 1-7. 言語リストをハードコードしない — ADR 0025

`src/ebmcg/` / `src/ebmip/` のディレクトリ列挙が SSOT で、`build_config.json` の
`TARGET_LANGUAGE` は廃止済み。18 個のバックエンドを追加/削除しても設定ファイルの更新漏れが
発生しない構造になっている。

### 1-8. ADR の「これは X を意味しない」節

48 本すべてに存在する。ADR 0047 の「コンパイル時間の削減ではない」、ADR 0048 の
「カバレッジが十分という意味ではない」「`Unexpected nullptr` が単一原因という意味ではない」は、
いずれも後から読む側 (人間・AI 双方) が踏みそうな誤読を先回りで潰している。
これはテンプレートの一節ではなく、実際に機能している防御である。

### 1-9. capability negotiation で境界をバイパスする — `S2J_CAPABILITY_DIRECT_AST_PASS`

**事実**: ebmgen は `.bgn` を入力にするとき `libs2j` を DLL として遅延ロードし
(`futils::platform::dll::DLL`、`libs2j_call` を名前解決)、`S2J_CAPABILITY_DIRECT_AST_PASS` を
立てて呼ぶ (`src/ebmgen/main.cpp:253`)。src2json 側の `do_direct_ast_pass()`
(`src/tool/src2json/src2json.cpp:374`) はこのケイパビリティが立っていればコールバックに
`brgen::ast::DirectASTPassInterface` (`std::shared_ptr<ast::Program>` / `FileSet` /
`SourceError` へのポインタ) を渡して `exit_ok` で返り、**`dump_json_file()` に到達しない**
(同 846 行)。ebmgen 側のコールバックは `IS_DIRECT_AST_PASS(is_error)` を最初に判定して
`shared_ptr` をそのまま受け取る。**成功パスで JSON のシリアライズ/パースは発生しない。**

**なぜ継承に値するか**: JSON AST という境界は json2go (Go) / json2rust (Rust) /
`astlib/ast2*` / LSP / web playground が今も消費しているので消せない。しかし C++ の
in-process 消費者 (ebmgen) にとってはテキスト往復が純コストである。ケイパビリティフラグで
**同じ DLL が消費者ごとに受け渡し形式を選ぶ**形にしたことで、境界を壊さずにコストだけ
外している。「多言語向けの境界を持つが、単一言語の消費者には払わせない」という解き方は、
0 から作る場合にもそのまま使える形をしている。

**残る JSON 経路**: `--input-format json` (JSON AST ファイル / stdin)、直接渡しが使えない
場合、およびエラー報告経路 (`--print-on-error` による JSON ダンプ)。ebmgen 側コールバックの
`load_json_file` 分岐はこのフォールバック用。

**限界**: `DirectASTPassInterface` の受け渡しは `sizeof` 一致でしか検証していない
(`size of DirectASTPassInterface mismatch`)。DLL と呼び出し側が同一ビルドから配置される
現在の運用では問題にならないが、DLL を別配布する構成にすると前提が変わる。

### 1-10. default 層は「default と称して実は上書きされている」状態になっていない

**測定** (default hook 99 個 × 18 バックエンドの override 行列):

| 観測 | 数字 |
| --- | --- |
| override 率が最大の default hook | **5/18** (`Expression_CAN_READ_STREAM` / `Statement_ENUM_DECL` / `Statement_STRUCT_DECL`) |
| 一度も override されない default hook | **37/99** |

**過半数の言語に上書きされている default hook は 1 つも存在しない。** 上限が 5/18 (28%) で、
37 個は全 18 言語がそのまま受け入れている。ADR 0003 の「言語非依存の展開を一箇所にまとめる」は
主張の再掲ではなく、この数字で確認できる。

override が 2/18 に留まる行はほぼ `ebm2c + ebm2rmw` または `ebm2llvm + ebm2rmw` の組で、
手動メモリ管理 / インタプリタ / SSA という**構造的に外れたバックエンドに集中**している。
つまり default の設定水準は「普通の手続き型言語」に合わせられており、それが多数派である限り
機能し続ける。

**再測定手順**: `src/ebmcodegen/default_codegen_visitor/visitor/` と
`src/ebmcg/*/visitor/` `src/ebmip/*/visitor/` のファイル名集合 (`_class` 接尾辞を除去) を
突き合わせるだけ。EBM 構造やフック追加のたびに再実行すれば、default 層の劣化を検知できる。

## 2. 再考の材料がある点

以下は「欠陥」のリストではない。**なぜ今そうなっているか**を先に書き、その上で 0 から作る場合に
別の選択肢がありうる箇所を、失うものと対にして並べる。

### 2-1. transform pass の依存が暗黙

**事実**: `transform/transform.cpp` は 15 パスを固定順で直列に呼ぶだけで、各パスが
**要求する前提条件**と**保証する事後条件**はコード上に宣言されていない。

```
flatten_io_expression → CFG → lowered_dynamic_bit_io(read) → (write)
→ merge_bit_field → vectorized_io(read) → (write) → derive_property_setter_getter
→ add_cast_func → derive_array_setter → derive_encode_decode_wrapper
→ propagate_io_input_desc → lower_runtime_state → [very_slow_bit_ops] → [remove_unused]
```

**徴候**: ADR 0048 の各「経過」節が、修正のたびに「より後段の別エラーへ移動した」件数を
記録している (`sort_test` → `RECURSIVE_STRUCT`、`propagate` → `lower_runtime_state`、
`media/ac3.bgn`・`ripple.bgn` → `bit_fields.cpp:72`)。前段の欠落が後段で顕在化する構造が
繰り返し観測されているということである。

同様に、`bit_fields.cpp` が unspec エンディアンの IOData を受け取って落ちていた件
(ADR 0048、61→58) は、「`encode_field_type` が埋めなかった属性を後段が前提にしている」という
**パス間の暗黙の契約**が破れたケースだった。

**0 から作るなら**: 各パスが requires/provides を宣言し、順序をビルド時または起動時に検証する。
「このパスの後は IOData の endian が unspec でない」といった不変条件を機械可読にする。

**失うもの**: 宣言の記述コスト。パス数が 15 で固定順が破綻していない現状では、これは純粋な
オーバーヘッドに見える。効果が出るのはパス数と相互依存が増えてからで、**今の規模では
コストが上回る可能性がある**。判断材料としては「過去 1 年でパス間契約の破れが何回起きたか」を
数えるのが妥当。

### 2-2. 出力が文字列連結である

**事実**: 各バックエンドは `CODE(...)` / `CODELINE(...)` で文字列を組み立てる。ターゲット言語の
構文木は持たない。

**帰結**: 以下が言語ごとに個別実装されている。
- 式の優先順位に応じた括弧付け
- 予約語・識別子衝突の回避
- ターゲットコンパイラの制約 (ADR 0043。`ebm2java` は JLS の到達可能性規則をバックエンド側で
  ミラーしている)

`project_interlang_dedup_survey` の調査でも、共通化不適と判定された群
(MEMBER_ACCESS / CAN_READ_STREAM / SUB_BYTE_RANGE / INIT_CHECK / LITERAL_INT) がある。

**なぜそうなっているか**: ADR 0026 の「何を切るか」と直結している。文字列連結は「とりあえず
出力が出る」までが速く、18 バックエンドの立ち上げ速度を支えてきた。18 言語の構文差を単一の
surface AST で吸収する設計は、それ自体が独立した設計課題になる。

**0 から作るなら**: 全面的な target AST ではなく、**最小の共通層**を検討する余地がある。
具体的には (a) 式の優先順位ノードと括弧付け、(b) 識別子エスケープ/予約語テーブル、の 2 点だけ。
制御フローや型宣言は文字列のままでよい。この 2 点は言語差が「テーブルの中身」に閉じており、
構造が共通しやすい。

**失うもの**: 新言語の立ち上げ速度。共通層に載せるということは、共通層が想定していない構文を
持つ言語 (ebm2llvm、ebm2p4、ebm2z3 のように「普通の手続き型言語」でないもの) が escape hatch を
必要とすることを意味する。ADR 0043 が「ターゲットコンパイラの制約はバックエンド側の責任」と
決めた線引きを一部引き戻すことになる。

**未測定**: 各言語のフックのうち、括弧付けと識別子エスケープに費やされている行数は数えていない。
これを数えれば「共通層に載せて何行減るか」が判断材料になる。数え方は
`src/ebmcg/*/visitor/` で優先順位・括弧・予約語に関連する箇所を grep して行数を集計する。

### 2-3. 言語固有の拡張点は kind hook ではなく config knob に寄っているが、文書は kind hook 中心のまま

**測定** (default が存在せず言語側にしかない hook の保有率):

| hook | 保有言語数 |
| --- | --- |
| `Flags` | 18/18 |
| `entry_before` | 15/18 |
| `pre_visitor` | 10/18 |
| `Visitor_before` | 9/18 |
| `Expression_MEMBER_ACCESS_before` | 8/18 |
| `Expression_LITERAL_INT_before` / `_INT64_before` | 各 4/18 |

対して kind hook (`Statement_*` / `Expression_*` の本体) の言語別実装は最大 5/18 (1-10)。

**読み取れること**: 拡張機構は ADR 0009 / 0016 で「priority 0 の言語別 kind hook が
priority 4 の default に勝つ」という優先順位システムとして設計・文書化されているが、
**実際に全言語が使っている拡張点は `entry_before_class.hpp` での `std::function` knob 設定**
(`Flags` 18/18 + `entry_before` 15/18) である。kind hook の置き換えは例外的な手段になっている。

**文書とのずれ**: `AGENTS.md` は `src/ebmcg/ebm2<lang>/visitor/` を
「**Where you write code** -- hook implementations」と説明し、続く節で `DEFINE_VISITOR(HookName)`
の書き方を示している。これは間違いではないが、実測上の主要導線ではない。実践側の判断は既に
knob 側へ寄っており (共有 `Visitor.hpp` に空デフォルトの knob を足す方針)、
**運用が先に動いて文書が追随していない**状態である。

**0 から作るなら**: 拡張点の第一級市民を config knob 側に置き、kind hook を
「knob で表現できない構造差のための escape」として位置づける。現在の優先順位システムは
そのままでよく、変えるべきは**どちらを既定の導線として提示するか**である。

**失うもの**: 特にない (機構の変更ではなく提示順の問題)。ただし knob を第一級にすると、
共有 `Visitor.hpp` の knob 数が増えて「全言語が知るべき設定面」が肥大する方向に圧力がかかる。
knob 追加の基準 (単一言語の compiler quirk は knob 化しない) を併記する必要がある。

**注意**: `Expression_MEMBER_ACCESS_before` の 8/18 は「共通化できていない」ではなく
「共通化が不適と判定済み」である (言語間重複調査で MEMBER_ACCESS は共通化不適の判定)。
この行を削減対象と読まないこと。

### 2-4. `_zc` 生成物がツリーに存在するが参照されていない

**事実**: `src/ebm/extended_binary_module_zc.hpp` (5,954 行) と `..._zc.cpp` (25,936 行) は
非 zc 版と `namespace ebm` / `namespace ebm::zc` の違い以外ほぼ同一である
(`diff` 出力がそれぞれ 12 行 / 8 行)。生成元は `src/ebm/ebm.py` の `zc_overrides`。
リポジトリ内を全文検索した限り、この 2 ファイルを include している TU は存在しない
(ヒットは `ebm.py` 自身と `save/codeql-db/` のみ)。

**なぜそうなっているか (推測を含む)**: zero-copy 版の先行生成と思われるが、ADR には記録がない。
意図的な準備なのか、実験の残りなのかは実装からは判断できない。**ここは判断せず質問する**
(AGENTS.md「NEVER make arbitrary decisions」)。

**関連**: ADR 0047 は同種の重複 (per-lang 生成物 150 万行) を共有 body + wrapper で解消済み。
zc 対は同じ機構が適用されていない残りの実例である。仮に将来 zero-copy 版が必要になるとしても、
`CODEGEN_NAMESPACE` 相当のパラメータ化で 1 部に畳める形をしている。

### 2-5. 死蔵資産の位置づけ

**事実**: `src/candidates/` に BM 時代の生成器スケルトンが 34 個、`src/old/` に 122 ファイル。

**なぜそうなっているか**: AGENTS.md が「`src/old/` は legacy code」と明示しており、運用で
カバーされている。`src/candidates/bm2*` は将来の言語追加時の参考実装として残っている可能性がある
(bm2dfdl、bm2nail、bm2trunnel、bm2sbe など、ebmcg にまだない対象を含む)。

**0 から作るなら**: 別ブランチまたはアーカイブ用リポジトリに置く。ツリーに残す判断は
grep ノイズと引き換えである。ただし現状 AGENTS.md の「検索範囲」指示で実害は抑えられており、
**優先度は低い**。

## 3. 作り直しても変わらないもの

作り直しの議論で「アーキテクチャの問題」に見えるが、実際は対象領域から来ている制約。

### 3-1. 共通 4,033 行 : 言語固有 22,100 行 という比

これはメタ生成機構の不足ではない。15 言語の型システム・所有権モデル・エラー処理・
ビット操作の差そのものが 22,100 行である。ebm2c (2,557) / ebm2go (2,833) / ebm2rust (2,434) /
ebm2llvm (2,307) が上位に来るのは、それぞれ (手動メモリ管理 / GC + interface / borrow checker /
SSA + 型付きポインタ) という**互いに直交する制約**を持つからで、共通層に押し込めるものではない。

作り直しでこの比が大きく改善すると期待するのは、根拠がない。

### 3-2. 変換できない `.bgn` 58 件

ADR 0048 の作業リスト。これは IR 設計の問題ではなく変換実装の未着手部分であり、
アーキテクチャを変えても件数は減らない。フレーム単位で 35 グループという粒度も同じ。

### 3-3. `.bgn` を入口にすること

ADR 0026 の「切った軸」がここに全部乗っている。作り直しの対象ではなく、作り直しの前提。

## 4. まとめ (優先度は付けない)

**継承**: ADR 0003 (意味論保存 IR) / 0004 (DSL による IR 定義) / 0019 (C++ 統一) /
0025 (言語リスト非ハードコード) / 0026 (切る判断の明文化) / メタ生成 + フック優先順位 /
capability negotiation による境界バイパス (1-9) / default 層の健全性 (1-10) /
測定駆動 / 「これは X を意味しない」節。

**再考の材料あり**: transform の暗黙依存 (2-1) / 文字列連結の共通層不在 (2-2) /
拡張点の提示順と実態のずれ (2-3) / `_zc` 重複 (2-4) / 死蔵資産 (2-5)。

**実害の記録がある項目はゼロである。** 2-1 は徴候はあるが実害としては未計上。
2-3 は機構の問題ではなく文書の追随遅れ。初版で唯一「実害あり」としていた
`ConverterState` の項は、事実誤認だったため削除した (訂正履歴参照)。

**未決 (人間の判断が要る)**:
- 2-4 の `_zc` は意図的な先行生成か、実験の残りか。
- 2-2 の共通層導入は、まず「括弧付け・識別子エスケープに何行使われているか」を測ってから。
- 2-1 の依存宣言化は、「パス間契約の破れが年に何回起きたか」を数えてから。

## この文書の限界

**§1 の大半は ADR からの導出であり、新情報を含まない。** ADR は定義上「既に下した判断」の
記録なので、そこから作った要約が書き手にとって未知であることは構造的にありえない。
数字を添えても「ADR の主張と矛盾しない」ことの確認にしかならない。

非自明な内容は、**ADR が横断していない軸で測ったもの**に限られる。現時点でそれに該当するのは
1-10 と 2-4 (hook override 行列) のみである。同種の測定を足すなら、ADR が単体では答えていない
横断的な問いを選ぶこと。例:

- EBM のノード種別ごとに、何言語がその展開を default に委ねているか (support matrix の疎密)
- transform pass ごとの、生成 IR ノード数の増減 (どのパスが IR を膨らませているか)
- 各バックエンドの hook 行数のうち、括弧付け・識別子エスケープが占める割合 (2-3 の判断材料)

## 訂正履歴

- 2026-08-05: 初版で「フロントエンド境界が JSON テキストのまま」を再考項目 (旧 2-1) として
  挙げたが誤り。`S2J_CAPABILITY_DIRECT_AST_PASS` の制御フローを読まずに、コールバック内の
  `load_json_file` 呼び出しだけを見て書いていた。実際には `.bgn` 入力の成功パスは
  `shared_ptr<ast::Program>` の直接受け渡しであり JSON 往復は発生しない。1-9 として
  継承側に移した。
- 2026-08-05: 初版の「`ConverterState` の暗黙プロトコル」(旧 2-1) を削除。
  「進入・退出は呼び出し側の規律で維持されている」は事実に反していた。全フィールドは
  `private` で、状態の出入りは `futils::helper::defer` による RAII ガード 13 個
  (うち 11 個が `[[nodiscard]]` 付きの `enter_*` / `set_*` / `scoped_endian`) を通してのみ
  行われる。ガードを捨てると警告になる。**初版が「0 から作るなら」として挙げた案
  (生フィールドを private 化し RAII 経由でのみ変更可能にする) は現状そのものだった。**
  ADR 0048 の動的エンディアン障害もこの構造由来ではなく、`converter.cpp:48` の
  `// UNFINISHED, not dead: nothing calls set_on_function()` が示すとおり、BM から
  フィールドだけ移植されて進入フックが来なかった移植漏れである。RAII 機構は関与していない。
- 2026-08-05: 初版の「`get_field<"path">` の検出タイミングの穴」(旧 2-5) を削除。
  `access_helper.hpp` の `get_field_index` は不正なフィールド名に対し
  `if (std::is_constant_evaluated()) { throw "No such field"; }` を実行するため、
  定数評価文脈でのハードなコンパイルエラーになる。パス解決には ref の型解決が必要なので、
  「パス文字列を収集して EBM 定義と突き合わせる」案はコンパイルより厳密に弱い。
  ADR 0025 により全言語がディレクトリ列挙からビルドされるため、CI で全て当たる。
  検出装置として不足はなかった。
