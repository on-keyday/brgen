# 言語内テストとエラー処理

2026-08-27 の議論のメモ。結論は出ていない。測ったものと、測っていないものを分けて残す。

## 出発点

テストが `unictest` などの外側に限定されている。`.bgn` そのもので
「この値を符号化するとこのバイト列になる」「このバイト列を復号するとこうなる」
を書けると嬉しい、という要求。

## 言語内テストに要るもの

台帳 (`spec/features.json`) と突き合わせた結果:

| 要るもの | 現状 |
| --- | --- |
| バイト列を書く | **ある** F0003 (`"\xNN"`) |
| 値に名前を付ける | **ある** F0041 (`::=`) / F0042 (`:=`) |
| 比較する | **ある** F0078。失敗させるなら F0038 (アサーション) |
| **format の値を組み立てる** | **無い**。`Foo{...}` のような構築構文が無い |
| **encode / decode を呼ぶ** | **無い**。F0052 は手書きで定義する側で、呼ぶ側が無い |
| **失敗するはずを書く** | **無い** |

足りないのは 3 つで、**エラー処理はそのうちの 1 つ**。手前の 2 つのほうが根が深い。
今の `.bgn` は入力を読む記述しか書けず、**値を作る側の言語ではない**。

3 つには順序がある:

1. **値を組み立てられる** — 無いと符号化する対象が無い。入れると言語の性格が変わる
   (読む記述から、値も作れる記述へ)
2. **encode / decode を呼べる** — 無いと往復できない。`input` / `output` を明示的に
   扱う話なので、IO 操作の型付けと直結する
3. **失敗するはずを書ける** — 否定テスト。ここでエラー処理が要る

F0027 (固定値フィールド `fixed :u8(0x12)`) は既に「この位置にはこの値が来るはず」を
宣言していて、読む側から見た期待値の記述になっている。テストが欲しいものと近い。

## エラー処理

### 今あるもの

| | |
| --- | --- |
| 発生 | F0038 アサーション、F0040 `error()` |
| 処理 | F0034 (対象を書かない `match`。各分岐を順に試し、読めたものを採る) |
| 無い | 失敗を値として受ける、失敗理由で分岐する |

F0034 は失敗を「試行の打ち切り」として使う形で、失敗が値になっていない。
「失敗したら残りを raw bytes で読む」のような回復は
`.. => opaque :[..]u8` で既に書ける (`.. =>` は 41 ファイル、`[..]T` は 340 件)。
**回復規則を増やす方向 (宣言的なまま) には空きが無い。**

### 効果か値か

失敗を「型の外の効果」にするか「型の世界の値」にするか。

| | 効果 | 値 |
| --- | --- | --- |
| 失敗を保存・持ち回り | できない | できる |
| 失敗を集めて後で判断 | できない | できる |
| バックエンドが作るもの | 呼び出し境界だけ | 値が現れる全ての場所 |
| EBM との距離 | `ENCODER_RETURN` / `DECODER_RETURN` が既にこれ | 新しい型種が要る |

**「符号化できない型が言語に入る」は反対理由にならない。** `bool` は既にそうで、
コーパスの 13 件は全部 `state` ブロックの中にある (`state` は 38 件)。
線上表現を持たない型は既にあり、**書ける文脈を分ける**ことで共存している。
失敗を値にする場合も同じ扱い (フィールドには置けない) で足りる。

### コーパスが言うこと / 言わないこと

`error()` 41 件の中身:

```
引数 1 個 (メッセージだけ)   36 件
引数 2 個 (値を添える)        5 件   error("unknown section type: ", sectionType)
```

- 失敗を値として持ち回った実例は **0 件**
- 失敗理由を種類で区別した実例も **0 件**。`unknown ... type` / `invalid ...` /
  `unexpected ...` が大半で、区別を付けていない
- 値が渡される 5 件は診断メッセージに埋め込むためで、上位で分岐に使っていない

**ただしこれは現状の写しであって、要求の写しではない。** 言語として書けないものは
`.bgn` に現れようがないので、「使われていない」は「要らない」の証拠にならない。
この測定で言えるのは「既存資産を移行する動機は無い」まで。

言語内テストの否定テスト (3) は、まさに**書けないから書かれていない**側の実例。

## fn の失敗しうる性

`fn` の戻り値に「失敗しうる」の印を付ける件。

```
Assert         368 件   fn の中  56  /  fn の外 312   (115 ファイル)
ExplicitError   41 件   fn の中   7  /  fn の外  34
```

`assert` というキーワードは無い。**文の位置に真偽演算子の式を書いたものが `Assert`**
になる (`parse.cpp:2003`)。85% は format の本体直下。

**format の encode/decode は常に errorable なので、そちら側に解析は要らない。**
計算が要るのは `fn` の戻り値だけ。

伝播の要否を固定点まで回して測った:

```
fn 203 個
  本体に直接 assert/error   37
  他の fn を呼ぶ            16   (うち直接も持つ 5)
  伝播後に失敗しうる        39   ← +2
```

**伝播はほぼ効かない。** `fn` が `fn` を呼ぶこと自体が 203 個中 16 個。
局所判定で 37/39 を拾える。伝播の実装コスト (呼び出しグラフ + 固定点 +
相互再帰の停止) に見合わない。ただしこれはコーパスの性質であって言語の性質ではない。

## 次に着手するなら

**IO 操作の型付けが最初。** 理由は 2 つ:

- 型カバレッジの最大の塊。`SpecialLiteral 671` (0%) と `Call 701` (10.5%) が
  ほぼこれ。`input.subrange` 209 / `config.endian` 149 / `output.put` 67 /
  `input.get` 59 など、コーパスで 550 件超
- 言語内テストの 2 (encode/decode を呼ぶ) の土台になる

木は既にその形になっている:

```
Call
  callee: MemberAccess
    base:   SpecialLiteral(input_)
    member: Ident("get")
  arguments[0]: TypeLiteral { type: MetaType, literal: IntType(u8) }
```

`u8` は既に `TypeLiteral` で `literal` に実体が入っているので、
**「戻り値は引数 0 が名指す型」という規則 1 つ**で書ける。型パラメータは要らない。

組み込みメンバ表の戻り値規則:

| メンバ | 戻り値 |
| --- | --- |
| `get` / `peek` | 引数 0 の TypeLiteral が名指す型 |
| `offset` / `bit_offset` / `remain` / `scope_length` | u64 |
| `subrange` | 同じストリーム型 |
| `backward` | void |
| `output.put` | void |

副産物として `input.foo` のような未定義メンバがエラーになる (今は静かに何も起きない)。

判断が要るのは `input` 自身の型。`StreamType` を新設するか、既存で代用するか。
`config.endian = "big"` はメンバアクセスへの代入で形が違い、元の実装では
`Metadata` になる。別扱いが要る。
